## Чек-лист перед публикацией статьи о ПП 719 / ПП 1875 / ГИСП / ТПП

### 1. Термины национального режима (ПП 1875) — самая частая ошибка
- Запрет, ограничение и преимущество нигде не описаны как «варианты одного 
  механизма» или «меню из трёх опций для одной позиции»
- Приложение №1 = запрет (не требует наличия конкурирующей заявки); 
  Приложение №2 = ограничение, оно же «второй лишний» (требует наличия хотя 
  бы одной надлежаще подтверждённой заявки); преимущество — отдельно, 
  ценовая мера
- «Второй лишний» не описан как отдельный, четвёртый механизм наравне 
  с запретом/ограничением

### 2. Балльная система / позиции ПП 719
- Нет фраз «баллы устанавливаются одинаково для всей отрасли» — конкретные 
  баллы/условия всегда привязаны к позиции ОКПД2
- Если позиция ссылается на «из [код]» — проверено, не объединяет ли эта 
  строка/группа строк разнородные категории с разными требованиями
- Не спутаны «баллов нет» и «требований по доле иностранных товаров нет» — 
  это разные вещи

### 3. Медицинские изделия и классификаторы
- Для МИ явно указано, что одного ОКПД2 недостаточно — нужен код вида МИ 
  по НКМИ, если он указан в позиции
- КТРУ не описан как «альтернативный классификатор, обязанный совпасть» 
  с ОКПД2 реестровой записи

### 4. Даты и сроки — проверять особенно внимательно
- Если статья ссылается на дату вступления акта в силу — сверено, что дата 
  публикации статьи не позже этой даты
- Если акт вносит изменения несколькими пунктами с разными датами — явно 
  проверено, какой пункт к какому разделу относится
- Проверочные/уведомительные сроки взяты из текста нормы, а не выведены 
  интуитивно

### 5. Обобщение практики до нормы
- Рядом с «автоматически», «всегда», «в большинстве случаев», «эксперт 
  немедленно распознаёт» — либо точная ссылка на пункт нормы, либо явная 
  пометка «практическое наблюдение / рекомендация», а не норма

### 6. Кейсы
- Реальный кейс — есть номер закупки/решения ФАС/дата, иначе кейс явно 
  называется «обезличенный пример» / «условный пример»

### 7. Технические проверки перед публикацией
- Новая статья собрана на основе актуального опубликованного шаблона 
  (canonical, og-теги, JSON-LD, полное меню, футер) — не скопирована 
  со старого файла
- JSON-LD (Article + FAQPage) синхронизирован с видимым текстом, особенно 
  при капитальной переработке
- Все использованные CSS-классы определены в <style> файла

## Брендинг
- Название компании/бренда в title, meta-og:title, логотипе, header, footer, 
  JSON-LD organization/publisher — всегда короткое: "Инженерный центр".
- В содержательном тексте статей допустимо использовать полное "Инженерно-
  регуляторный центр" как описательную фразу — это не ошибка.

## Как добавлять карточку статьи в блог (`/blog/index.html`)

**Новые карточки добавлять только через `scripts/add-blog-card.js`** — он проверяет рубрики (1–3 из списка ниже), вставляет карточку первой в `blog/index.html` и добавляет запись в `sitemap.xml`:

```bash
node scripts/add-blog-card.js --slug <slug> --title "<H1>" --desc "<description>" --date ГГГГ-ММ-ДД --label "ПП 719 · Баллы · ПО" --tags "pp719 bally" [--dry-run]
```

Ниже — формат результата (для справки и проверки; руками карточку не писать).

Одна карточка на одной строке внутри `<div class="grid g3" id="blog-grid">`. Скрипт сам ставит карточку на её место по дате (новые первыми; свежая статья окажется первой). Порядок карточек = порядок по дате публикации; в любом фильтре он сохраняется автоматически, отдельно сортировать ничего не нужно.

Формат (копировать с соседней карточки, менять только текст и атрибуты):

```html
<a class="card" href="/blog/<slug>" data-tags="pp719 bally" style="display:flex;flex-direction:column;gap:9px;transition:.2s;text-decoration:none"><span style="…">Кикер · до трёх слов</span><h3 style="…">Заголовок (H1 статьи)</h3><p style="…">Описание (= description статьи)</p><span style="font-size:12px;color:var(--muted)">6 октября 2026</span><span style="font-size:13px;font-weight:700;color:var(--orange)">Читать →</span></a>
```

- Атрибут `data-tags` — **список рубрик через пробел** (не `data-tag`!), от 1 до 3 рубрик. Фильтр показывает карточку, если выбранная рубрика есть в списке; «Все» показывает всё. Ни одна карточка не должна остаться без рубрики.
- **Дата** — предпоследний `<span>` карточки, формат «6 октября 2026». **«Читать →»** — последний `<span>`; он всегда на отдельной строке под датой, отступ задаёт общее CSS-правило `#blog-grid .card>span:last-child` — инлайном его не дублировать.
- Новые рубрики не добавлять без отдельного решения. Допустимые значения и правила:

| Значение | Рубрика | Что сюда относится |
|---|---|---|
| `pp719` | ПП 719 | подтверждение производства, локализация, адвалорная доля, баллы, РРПП, ТПП, СТ-1, смена поставщиков |
| `bally` | Балльная система | разбор баллов конкретных позиций или расчёт баллов (КТ/УЗИ, датчики, PCB/SMT, firmware, аферез, протезы, операционное оборудование и т. п.) |
| `krov` | Служба крови | гемоконтейнеры, аферез, плазмаферез, донорская кровь, тесты для доноров, центрифуги, трансфузиология |
| `gisp` | ГИСП и отчётность | отчёты в ГИСП, исключение и продление реестровой записи, проверки ТПП |
| `goszakupki` | Госзакупки и нацрежим | ПП 1875, КТРУ/ОКПД2, закупки, аванс, ответственность заказчика, смешанные лоты, переходный период |

- Рубрики определять **по содержанию статьи**, а не по кикеру на карточке.
- Вместе с карточкой — запись в `sitemap.xml` и обратные ссылки в «Читайте также».

## Проверка перед каждым коммитом

Перед каждым коммитом, который затрагивает `.html`, `sitemap.xml` или `blog/index.html`, запускать:

```bash
node scripts/check-site.js
```

Код возврата 1 = есть ошибки, коммитить нельзя. Проверяется: валидность JSON-LD; битые внутренние ссылки; **каждая `<table>` внутри обёртки `<div style="overflow-x:auto">…</div>` (иначе ошибка)**; sitemap (все статьи блога есть, нет дублей, корректный `lastmod`); карточки блога (у каждой статьи есть карточка, `data-tags` 1–3 рубрики, порядок по дате); `FAQPage` в JSON-LD = видимый FAQ дословно (видимый текст — первоисточник). В исключения `NOT_IN_BLOG` внутри `scripts/check-site.js` можно вносить только статьи, которые намеренно не должны быть в sitemap и блоге (дубли, служебные страницы), каждую с причиной.
