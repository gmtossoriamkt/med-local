# Статья для med-local.ru: от строки контент-плана до PR

Работаешь в репозитории med-local.ru. Цель — достоверная, SEO-оптимизированная статья, опубликованная через PR. В main напрямую не пушишь никогда: публикация = merge PR владельцем.

## 0. Выбор задачи

1. Открой `content-plan.csv`. Если в запросе указан номер статьи — бери его, иначе первую строку со статусом `todo` (по порядку номеров).
2. Создай от свежего main рабочую ветку `blog/<номер>-<короткий-слаг>`, поставь статус `in-progress`.
3. Если есть `factcheck/<номер>.md` — это фактчекинг редактора: учти все его замечания, рекомендованный заголовок и структуру. Фактчекинг — тоже вторичный источник: его утверждения проверяются, как и твои (в нём бывают ошибки в реквизитах и датах).
4. Если фактчекинга нет — сначала сделай его сам: какие правовые режимы смешаны в теме, какие тезисы рискованны, какой заголовок не обещает лишнего.

## 1. Исследование

- Первоисточники: zakonrf.info, docs.eaeunion.org, roszdravnadzor.gov.ru, библиотека `med-local-biblioteka`. pravo.gov.ru / government.ru из облака обычно недоступны — не больше одной попытки.
- Вторичные источники (ppt.ru, новости garant/consultant, pharmvestnik, alta.ru) — только как подсказка. Факт, найденный только в них, подаётся мягко («по опубликованным обзорам…») или не подаётся.
- Посмотри, что уже написано на сайте по теме (grep по номерам пунктов и актам), и не противоречь без причины. Если сайт где-то ошибается — не правь чужие статьи, а внеси это в отчёт.

## 2. Текст

Формат (как в существующих статьях):
- H1 — заголовок; строка байлайна: `А.-Т. Танделов, CEO ГМТ · Аудитор ISO 13485/14971 · Член АУСОМИ · Опубликовано: <дата>`.
- Блок **«Суть в четырёх предложениях»** — ровно четыре предложения с главным ответом на интент.
- Короткое вступление (2–3 предложения), 1–2 ссылки на связанные статьи сайта.
- Разделы H2, таблицы там, где идёт сравнение; практический чек-лист или порядок действий.
- FAQ из 5 вопросов (H4 + ответ в 1–3 предложения).
- CTA ГМТ → `/localization/` (или страница по теме).
- `### Нормативная база` — полные реквизиты, редакции, номера пунктов.

Правила содержания:
- Каждый конкретный факт (номер пункта, дата, срок, порог, баллы) — только если подтверждён первоисточником. Нет подтверждения — обобщи или убери.
- Разводи режимы: ПП 719 (российская промпродукция) ≠ ПП 1684 (регистрация МИ) ≠ ПП 1236 (реестр ПО) ≠ ПП 1875 (закупки) ≠ ПП 878 (РЭП).
- Критерии ПП 719 зависят от конкретной позиции раздела VII — не переноси критерии одной позиции на другую.
- Не обещай результат («получите баллы», «регистрация не нужна») — пиши условия.
- Тон эксперта-практика, без воды; русская типографика (« », —).
- Объём — как в контент-плане (обычно 5500–8000 знаков).

## 3. Шаг 0 — сверка

Перед сборкой страницы пройди по тексту и для каждого факта отметь: подтверждено (источник, пункт) / исправлено / убрано. Сохрани это как отчёт — он пойдёт в описание PR.

## 4. Сборка страницы

1. `node scripts/mk-article.js <конфиг.json>` — по текущему шаблону из main (актуальная шапка с телефоном). Конфиг: `slug`, `md`, `template` (путь к последней опубликованной статье, например `blog/<slug>/index.html`), `title`, `desc`, `kicker`, `crumb`, `date` (ГГГГ-ММ-ДД), `dateRu`, `faqCount`, `mailSubject`, `mailButton`, `related` (`[[href, текст], …]`). Конфиг и черновик `.md` держи вне репозитория.
2. Адрес `/blog/<slug>/` — латиница, со слэшем на конце.
3. Title ≤ 60 символов, description ~150 символов; не дублируют ключи соседних статей (проверь grep по title).
4. Разметка `Article` (как у всего блога) + FAQPage в JSON-LD; вопросы дословно совпадают с текстом.
5. Таблицы — в адаптивной обёртке.
6. Карточка в блог: `node scripts/add-blog-card.js`.
7. Обратные ссылки: в 2–5 тематически близких статьях — по одному предложению со ссылкой, без переписывания и без смены их дат.
8. sitemap.xml обновлён (скриптом или вручную).

## 5. Проверки

- `node scripts/check-site.js` — 0 ошибок; `bash scripts/check-injections.sh` — 0 находок.
- Локально через `node scripts/srv.js` (порт 8766): страница отвечает 200, на ширинах 1280 и 375 нет горизонтальной прокрутки, все ссылки рабочие, FAQ = JSON-LD.
- Если проверка красная — исправь и повтори. PR с красными проверками не открывай.

## 6. PR

1. Статус в `content-plan.csv` → `pr`, в колонку `url` — адрес статьи.
2. Коммит, пуш ветки `blog/...` (пуш рабочей ветки разрешён, в main — нет).
3. PR в main по шаблону `.github/pull_request_template.md`. В облачной сессии `gh pr create` не работает (GraphQL закрыт) — открывай через REST: `gh api repos/gmtossoriamkt/med-local/pulls -f title='blog: <№> <тема>' -f head='blog/<ветка>' -f base='main' -f body="$(cat <файл с описанием>)"` (для черновика добавь `-F draft=true`). Удалять ветки из сессии нельзя — не пытайся. Заголовок: `blog: <№> <тема>`. В описании:
   - адрес, title и description;
   - отчёт шага 0: «подтверждено / исправлено / убрано»;
   - что осталось непроверенным и почему;
   - изменённые файлы и статьи с обратными ссылками;
   - адреса для переобхода в Яндекс.Вебмастере: новая статья, /blog/, статьи с обратными ссылками.
4. В конце сессии — короткий итог со ссылкой на PR.

## Если что-то пошло не так

- Тема юридически некорректна, а фактчекинга нет → напиши статью с исправленным заголовком и объясни это в PR.
- Первоисточник по ключевому тезису недоступен, а смягчить тезис нельзя → открой PR как draft (`-F draft=true` в `gh api …/pulls`) и пометь, что нужно решение человека.
- Ничего не пушь в main и не меняй workflow деплоя.
